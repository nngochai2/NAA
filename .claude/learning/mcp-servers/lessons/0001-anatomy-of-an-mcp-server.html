MCP Servers · Lesson 1

The Anatomy of an MCP Server

Open two files in your own repo: mcp/jira/jira_mcp/server.py and mcp/src/server.py (the knowledge-graph server). They both do the same job — expose tools to an AI agent — and they look almost nothing alike. One hand-writes JSON Schemas and wires up Starlette routes by hand. The other slaps a decorator on a plain Python function. Neither is wrong. By the end of this lesson you'll know exactly why they differ, and be able to choose deliberately next time instead of copying whichever file was open.

1. Host, client, server

MCP defines three roles. Get these three nouns exactly right — almost every later confusion in this topic comes from blurring them.

  • Host — the LLM application the human is using. Claude Desktop, Claude Code, an IDE plugin. It's the thing that decides when to talk to a server.
  • Client — a connector living inside the host, one per server it talks to. It speaks the wire protocol. You never write this — the host provides it.
  • Server — what you write. A process that exposes capabilities (tools, resources, prompts) over a well-defined transport.

When you run python mcp/jira/jira_mcp/server.py, you are starting a server. Claude Code, connecting to it, is the host, and it maintains a client internally for that connection. All messages between client and server are JSON-RPC 2.0 — a lightweight request/response format, not a REST API. That's why you never see HTTP verbs like GET/POST in the tool-handling code itself; you see method names like tools/list and tools/call instead.

2. Three things a server can offer

The spec's server features page defines exactly three primitives. The critical distinction is who decides to invoke it:

PrimitiveInvoked byShapeIn your repo
Tool The model, autonomously A function call: name + JSON Schema args → result Every server in mcp/ today — jira_get_issue, search_notes, etc.
Resource The app or user, like a GET request A URI → content, read-only, no side effects Unused so far — a candidate for codegraph's read-only file/graph views instead of a tool
Prompt The user, explicitly (e.g. a slash command) A reusable templated message Unused so far
Why this matters for you
Every one of your six servers only exposes tools. That's a defensible default (tools are the most flexible primitive), but it's worth noticing it's a default, not a law. Read-only lookups like get_graph_stats() or jira_get_issue are arguably resources in spirit — the spec's own guidance is that resources suit "application-controlled" read access better than model-invoked tools. You've been vibecoding everything as a tool because that's the pattern you saw first.

3. Transport: how the bytes actually move

JSON-RPC messages need a pipe to travel over. MCP supports a few:

  • stdio — server is a child process, messages go over stdin/stdout. Simplest, used when host and server run on the same machine (e.g. Claude Desktop launching a local server).
  • SSE (Server-Sent Events) — server runs as an HTTP service; the server pushes messages over an SSE stream and the client posts back to a separate endpoint. This is what every server in mcp/ uses today.
  • Streamable HTTP — the direction the spec is moving in for remote servers, replacing raw SSE with a single HTTP endpoint that can stream. Worth watching: see the 2026-07-28 release candidate notes in RESOURCES.md.

Look at mcp/jira/jira_mcp/server.py: it builds an SseServerTransport("/messages/") and mounts it onto a Starlette app by hand. Look at mcp/src/server.py: it just calls mcp.run(transport="sse") at the bottom. Same transport, same wire format — wildly different amount of code, which brings us to the real point of this lesson.

4. Two APIs, one SDK

Both files import from the same package — mcp==1.27.x, the official Python SDK. It ships two layers:

Low-level: mcp.server.Server — what jira_mcp/server.py uses

server = Server("jira-mcp")

@server.list_tools()
async def list_tools():
    return ISSUE_TOOLS          # you hand-build Tool() objects with raw JSON Schema

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    return handle_issue_tool(name, arguments, client=get_client(), ...)

# ...and you wire the Starlette/SSE app yourself:
sse = SseServerTransport("/messages/")
async def handle_sse(request):
    async with sse.connect_sse(...) as (read, write):
        await server.run(read, write, server.create_initialization_options())

You write the JSON Schema explicitly (ISSUE_TOOLS in jira_mcp/tools/issues.py), one if name == "..." dispatch block, and the transport plumbing. More code, but total control — useful when, like jira's server, you need custom logic threaded through (parent-issue resolution, link-type lookups) that doesn't fit a single decorated function cleanly.

High-level: mcp.server.fastmcp.FastMCP — what mcp/src/server.py uses

mcp = FastMCP("Knowledge Graph", host=HOST, port=PORT)

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def search_notes(query: str, limit: int = 10) -> str:
    """Search the knowledge graph by keyword. ...

    Args:
        query: Keyword to search for.
        limit: Max results to return (capped at 50).
    """
    ...

if __name__ == "__main__":
    mcp.run(transport="sse")

No hand-written schema, no dispatch block, no Starlette wiring. FastMCP reads your type hints and docstring and generates the JSON Schema and the routing for you. Less code, less control — you trade explicitness for speed, which is why this server, with its long flat list of independent read/write tools, reads so much more compactly than jira's.

The naming trap
There are two things called "FastMCP" in the wild: the class bundled inside the official SDK (mcp.server.fastmcp.FastMCP, what you're actually importing) and a separate PyPI package, fastmcp, by PrefectHQ, which is a superset with extra features (OAuth proxies, richer test clients) that later versions of the bundled one partially absorbed. Your requirements.txt files only pin mcp — you are not using the standalone package, even though tutorials you find online may be.
